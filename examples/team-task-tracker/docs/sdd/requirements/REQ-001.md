# Shared team tasks

## Problem and outcome

Fictional discovery interviews describe a team losing track of small shared work
items in chat. This is scenario context, not actual customer research. A member
needs one place to create a task, see the team's current tasks, and mark a task
complete without affecting another team's data.

## Scope

Include create, list and one-way completion in the existing team view. Exclude
editing, deletion, assignment, due dates, team management, notifications, offline
support, reopening and pagination. Identity/team membership and durable storage
are host-provided design assumptions described in the
[overview](../overview.md), not newly selected infrastructure.

## Functional requirements

- A team member can create a task with a short nonblank title.
- The team view lists open and completed tasks belonging to that team.
- Completing an open task makes its completed state visible; repeating completion
  does not create another task or cause an error solely because it is complete.
- Unauthorized users cannot read or mutate a team's tasks.

## Non-functional requirements and constraints

- All sensitive operations enforce membership on the server; a hidden button is
  insufficient. Public responses omit unrelated team/member information.
- The changed flow works with keyboard controls and meaningful labels/status.
- A rejected mutation leaves the last confirmed UI state intact and gives an
  understandable error. No latency target is invented without a host baseline.
- Reuse the host's supported stack, storage and identity conventions. A storage
  contract test must demonstrate the data behavior before claiming persistence.

## Acceptance criteria

### AC-001

A signed-in team member can create, see and complete a task in that team's view.
The same task remains completed on a subsequent successful list request.

### AC-002

An unauthenticated or non-member caller cannot read or change protected task data,
including by supplying a task ID from a different team.

### AC-003

Invalid input and rejected requests preserve confirmed data, show usable feedback,
and do not prevent a keyboard user from operating the form and task actions.

## Assumptions and open questions

The host-capability assumptions are accepted only for this design exercise.
Confirm their real interfaces, supported versions and commands before coding in
a real repository. No unresolved product behavior is silently assigned to an
implementer; a changed host constraint returns to planning/change control.
